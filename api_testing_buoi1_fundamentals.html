📱 PHẦN 1: API Là Gì?

🤔 Định Nghĩa (Theo Cách Của Tôi)

┌──────────────────────────────────┐ │ API = Application Programming │ │ Interface │ ├──────────────────────────────────┤ │ = Cách 2 applications nói │ │ chuyện với nhau │ │ = Bộ rules & protocols để │ │ giao tiếp │ └──────────────────────────────────┘

🏪 Ví Dụ Thực Tế: Nhà Hàng (Dễ Hiểu)

KHÔNG CÓ API (Cách Cũ): ├─ Bạn vào bếp trực tiếp ❌ ├─ Lục lỏi trong tủ lạnh ├─ Tự nấu nướng └─ Chaos! Đầu bếp nặn lun! CÓ API (Cách Mới): ├─ Bạn ngồi bàn (client) ✓ ├─ Đưa đơn hàng cho waiter (API) ├─ Waiter đưa đơn cho bếp (server) ├─ Bếp nấu & gửi lại waiter ├─ Waiter đem đến bàn bạn └─ Bạn nhận được food - Clean!
🔊 "Các bạn hãy tưởng tượng khi bạn vào một nhà hàng. Nếu KHÔNG có waiter (không có API), bạn phải tự vào bếp, lục lỏi trong tủ lạnh, tự nấu ăn - điều này rất nguy hiểm và bộn bề! Nhưng CÓ waiter (API), thì ngay, bạn chỉ cần ngồi bàn (là client), đưa đơn hàng cho waiter (API), waiter sẽ đưa đơn cho bếp (server), bếp nấu ăn và gửi lại waiter, waiter mang đến bàn bạn. Clean! Orderly! Professional!"

🔐 API Flow Trong Thực Tế: Login Example

┌─────────────────────────────────────────────┐ │ FRONTEND (Mobile App) │ │ ┌───────────────────────────────────────┐│ │ │ User bấm "Login" ││ │ └─────────────────┬─────────────────────┘│ │ │ │ └───────────────────┼───────────────────────┘ │ ▼ 📡 API REQUEST (HTTP) POST /api/auth/login { "email": "john@example.com", "password": "secret123" } │ ┌───────────────────┼───────────────────────┐ │ ▼ │ │ BACKEND (Server) │ │ ┌───────────────────────────────────────┐ │ │ │ 1. Validate email format │ │ │ │ 2. Check database │ │ │ │ 3. Verify password │ │ │ │ 4. Create session token │ │ │ │ 5. Return response │ │ │ └─────────────────┬─────────────────────┘ │ │ │ │ └───────────────────┼────────────────────────┘ │ ▼ 📡 API RESPONSE (HTTP) HTTP 200 OK { "status": "success", "token": "eyJhbGci...", "user": { "id": 123, "name": "John Doe" } }
🔊 "Khi user bấm nút Login ở app, frontend sẽ gửi một HTTP request tới backend server. Request này chứa email và password. Backend nhận request, validate input, kiểm tra database, xác minh password, tạo token (session), rồi gửi response về. Frontend nhận response, lưu token, và redirect user tới trang home. Cả quá trình này gọi là 'API call'."

🎯 Tại Sao Phải Test API? (Statistics từ 50+ projects)

📊 Các Con Số Thực Tế:

  • ✅ 70% bugs phát hiện từ API testing TRƯỚC khi UI test
  • ✅ 85% bugs backend không hiện ở frontend (UI mask logic)
  • ✅ 60% thời gian test manual là chờ data load (UI bottleneck)
  • ✅ API testing 5x nhanh hơn E2E testing
  • ✅ 40% cost saving khi focus vào API testing

💥 Ví Dụ Bug Chỉ Catch Qua API:

BUG #1: SQL Injection

API: GET /api/users?name=John

❌ VULNERABLE: /api/users?name=John' OR '1'='1
└─ Returns ALL users instead of filtering
└─ Frontend không test được (UI validation blocks)
└─ API test sẽ catch ngay!
BUG #2: Discount Bypass

API: POST /api/products/create
{ "name": "Laptop", "price": 1000000, "discount": 50 }

❌ Backend không validate discount range (should be 0-20%)
└─ UI có validation (max 20%)
└─ Bypass UI bằng API → 50% discount applied!
└─ Hàng tỉ losses!
🔊 "Các bạn ơi, từ kinh nghiệm 10 năm của tôi, tôi thấy rất nhiều bugs chỉ xuất hiện ở backend, nhưng frontend không bao giờ detect được vì frontend có validation bên UI. Ví dụ, nếu discount max là 20%, frontend sẽ limit input là max 20. Nhưng nếu attacker bypass UI, gửi discount = 50 trực tiếp tới API, backend không validate thì... toàn bộ discount 50% áp dụng! Hàng tỉ tiền losses! Chỉ API testing mới catch được điều này."

📡 PHẦN 2: REST vs SOAP vs GraphQL

REST (Representational State Transfer) - Thế Thượng Phổ Biến

🎯 Đặc Điểm REST:

  • Client-Server Architecture: Decoupled - client không care server
  • Statelessness: Each request contains all info needed
  • Uniform Interface: Use HTTP methods (GET, POST, etc) + status codes
  • Cacheability: Responses marked cacheable → Reduce server load
  • Layered System: API can call other APIs
  • Code on Demand (Optional): Server extend client functionality

REST API Examples (Từ Projects Thực Tế):

# Resource: Users GET /api/users # List all users GET /api/users/123 # Get user 123 POST /api/users # Create new user PUT /api/users/123 # Update user 123 completely PATCH /api/users/123 # Partially update user 123 DELETE /api/users/123 # Delete user 123 # Resource: Orders GET /api/users/123/orders # Get orders of user 123 POST /api/users/123/orders # Create order for user PUT /api/users/123/orders/456 # Update order
🔊 "REST rất đơn giản. Bạn hãy nhớ: mỗi resource là một 'thứ' (users, products, orders). Để thao tác với resource, ta dùng HTTP methods: GET (lấy), POST (tạo), PUT (update toàn bộ), PATCH (update một phần), DELETE (xóa). Rất logic! Rất dễ hiểu! Đó là lý do 80% APIs use REST."

✅ REST: Ưu & Nhược Điểm

✅ Ưu Điểm REST:

  • Simple, easy to understand (perfect cho beginners)
  • Stateless → Easy to scale (tạo nhiều servers)
  • Browser-friendly (test với URL trực tiếp)
  • Cacheable (reduce server load)
  • 80% APIs use REST (industry standard)

❌ Nhược Điểm REST:

  • Over-fetching: get extra data không cần dùng
  • Under-fetching: phải call nhiều endpoints
  • Versioning complexity (/v1, /v2, /v3)

📌 Ví Dụ Over-fetching:

GET /api/users/123 Response: { "id": 123, "name": "John", "email": "john@example.com", "phone": "+84912345678", ← Không cần "address": "123 Main St", ← Không cần "createdAt": "2024-01-01" ← Không cần }
🔊 "Over-fetching là vấn đề: Frontend chỉ cần id, name, email. Nhưng API trả về cả phone, address, createdAt - những thứ frontend không cần. Điều này gây lãng phí bandwidth, đặc biệt ở mobile networks. Tuy nhiên, REST vẫn là standard vì simplicity của nó."

📡 SOAP (Simple Object Access Protocol)

Định Nghĩa & Đặc Điểm:

SOAP = Protocol để exchange messages (XML-based)
Tư tưởng: RPC (Remote Procedure Call) style

SOAP cũ nhưng vẫn dùng trong Enterprise (Banking, Insurance)

📌 SOAP Request Example:

<?xml version="1.0" encoding="UTF-8"?> <soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/"> <soap:Body> <m:LoginRequest xmlns:m="http://api.example.com/"> <m:Email>john@ex.com</m:Email> <m:Password>secret123</m:Password> </m:LoginRequest> </soap:Body> </soap:Envelope>

SOAP Ưu & Nhược Điểm:

Ưu Điểm Nhược Điểm
✅ Standardized & secure ❌ Verbose (dài)
✅ Built-in error handling ❌ Slow (parse XML)
✅ WS-Security support ❌ Complex (tìm hiểu lâu)
✅ Enterprise support ❌ Not browser-friendly
🔊 "SOAP là cũ, nhưng nó rất mạnh trong enterprise. Ví dụ, khi bạn test API của ngân hàng hoặc bảo hiểm, bạn sẽ gặp SOAP. SOAP phức tạp hơn REST vì nó XML-based, nhưng nó có security features built-in. Chúng ta không sẽ deep dive vào SOAP, nhưng bạn cần biết nó tồn tại và cách nó khác REST."

🚀 GraphQL - The Modern Way

Định Nghĩa & Đặc Điểm:

GraphQL = Query Language để fetch exactly data you need
Tư tưởng: Client specifies exact fields needed

Giải quyết over-fetching & under-fetching problems

📌 GraphQL Request Example:

POST /graphql { "query": "query { user(id: 123) { id name email } }" }

GraphQL vs REST vs SOAP (So Sánh):

Tiêu Chí REST SOAP GraphQL
Phức Tạp Simple Complex Medium
Over-fetching ❌ Có ❌ Có ✅ Không
Under-fetching ❌ Có ❌ Có ✅ Không
Caching ✅ Easy ✅ Easy ⚠️ Hard
Adoption 80% 10% 10%
🔊 "GraphQL là tương lai nhưng chưa mainstream. Ưu điểm: bạn chỉ request exactly những fields cần thiết. Không over-fetch, không under-fetch. Nhưng disadvantage: caching khó, learning curve cao. Các startups/tech companies dùng (Shopify, GitHub), nhưng REST vẫn là standard."

🔧 PHẦN 3: HTTP Methods & Characteristics

📌 7 HTTP Methods Chính:

Method Purpose Idempotent Example
GET Fetch data (read-only) ✅ Yes GET /api/users/123
POST Create new resource ❌ No POST /api/users
PUT Replace entire resource ✅ Yes PUT /api/users/123
PATCH Partially update resource ❌ No PATCH /api/users/123
DELETE Remove resource ✅ Yes DELETE /api/users/123
HEAD Like GET but no body ✅ Yes HEAD /api/users
OPTIONS Describe API options ✅ Yes OPTIONS /api/users

🎯 Idempotency Concept:

Idempotent = Calling 1 time or 100 times = Same result

  • GET, PUT, DELETE are idempotent (safe to retry)
  • POST, PATCH are NOT idempotent (risk of duplicates)
🔊 "Idempotency rất quan trọng! Giả sử bạn gửi DELETE /api/orders/123. Lần đầu delete success. Nhưng connection timeout, client không biết success hay fail, nên retry lần 2. Vì DELETE idempotent, retry lần 2 = same result (order still deleted). Không bị delete twice! Nhưng POST không idempotent: gửi POST create order twice = 2 orders được tạo! Đây là lý do bạn phải test idempotency cho payment systems."

📊 HTTP Status Codes (Critical!)

🟢 2xx Success Codes:

Code Meaning When to Use
200 OK Request successful GET, PUT, PATCH success
201 Created Resource created POST success (new resource)
204 No Content Success but no response body DELETE success, PATCH

🔴 4xx Client Error Codes:

Code Meaning Example
400 Bad Request Malformed request (syntax error) Missing required field
401 Unauthorized Authentication failed Invalid credentials, no token
403 Forbidden Authenticated but no permission User can't access resource
404 Not Found Resource doesn't exist GET /api/users/999999
422 Unprocessable Request valid but logic error Email already exists
429 Too Many Requests Rate limit exceeded Too many login attempts

🔥 Critical: 401 vs 403 Difference:

401 Unauthorized: "Who are you?" (Prove identity)
Example: No token, invalid token, wrong password

403 Forbidden: "I know you, but you don't have permission" (Identity proven but access denied)
Example: User trying to access admin panel
🔊 "Difference giữa 401 vs 403 là critical ở interview! Hãy nhớ: 401 = authentication failed (bạn chưa prove ai mình), 403 = you're authenticated but no permission (tôi biết bạn là ai, nhưng bạn không được phép). Nếu test login và status không phải 401, bạn phải report lỗi!"

📨 PHẦN 4: Request/Response Structure

HTTP Request Structure:

POST /api/users HTTP/1.1 Host: api.example.com Content-Type: application/json Authorization: Bearer eyJhbGci... Accept: application/json Content-Length: 45 { "name": "Jane", "email": "jane@ex.com" }

HTTP Response Structure:

HTTP/1.1 201 Created Content-Type: application/json Server: nginx/1.18.0 Date: Mon, 20 May 2024 10:30:00 GMT Content-Length: 120 { "id": 100, "name": "Jane", "email": "jane@ex.com", "createdAt": "2024-05-20T10:30:00Z" }

🔑 Quan Trọng - Headers:

Header Purpose Example
Content-Type Data format application/json
Authorization Authentication token Bearer {token}
Accept Expected response format application/json
User-Agent Client info Mozilla/5.0...
Cache-Control Caching instructions no-cache, max-age=3600
🔊 "HTTP request/response giống một lá thư. Lá thư có phong bì (headers) và nội dung (body). Headers chứa metadata: loại data là gì (Content-Type), ai gửi (Authorization), etc. Body là actual data. Khi test API, bạn phải kiểm tra cả headers lẫn body!"

🧪 Test Case Design Framework

📋 Test Case Structure (Mandatory):

Test Case ID: TC001 Test Name: Login with valid credentials Endpoint: POST /api/auth/login Method: POST Input (Request Body): { "email": "john@example.com", "password": "Pass@123" } Headers: Content-Type: application/json Expected Result: - Status Code: 200 OK - Response contains: status = "success" - Response contains: token (JWT format) - Response contains: user object with id, name - Token should work for subsequent requests Verification Steps: 1. Assert status is 200 2. Parse response 3. Validate token format (JWT) 4. Verify user data structure 5. Store token for next test 6. Verify no sensitive data in response

🎯 Test Design Categories:

Cho Mỗi Endpoint, Design 4 Loại Test:

  • Happy Path (Positive): Valid input → Expected success
  • Negative Cases: Invalid input → Expected error
  • Boundary Cases: Edge values (min, max, empty, null)
  • Security Cases: SQL injection, XSS, authorization bypass
🔊 "Khi design test cases, bạn phải cover tất cả 4 categories. Happy path = everything works fine. Negative = what if user enter wrong password. Boundary = what if email is too long, password too short. Security = what if attacker try SQL injection. Nếu bạn miss bất kỳ category nào, bạn miss bugs. Và bugs sẽ go to production!"

📝 Example: 10 Test Cases for Login API

Endpoint: POST /api/auth/login

TC001: Valid Login ✅
Input: {email: "john@ex.com", password: "Pass@123"}
Expected: 200 OK + token returned
Verify: Status, token format, user data
TC002: Wrong Password ❌
Input: {email: "john@ex.com", password: "WrongPass"}
Expected: 401 Unauthorized
Verify: Status NOT 200, no token, generic error message
TC003: Non-existing Email ❌
Input: {email: "nobody@ex.com", password: "Pass@123"}
Expected: 401 Unauthorized (NOT 404!)
Verify: Same error as TC002 (avoid leaking email existence)
TC004: Missing Email ❌
Input: {password: "Pass@123"}
Expected: 400 Bad Request
Verify: Error message mentions required field
TC005: Invalid Email Format ❌
Input: {email: "not-an-email", password: "Pass@123"}
Expected: 422 Unprocessable
Verify: Format validation error
TC006: SQL Injection ⚠️
Input: {email: "' OR '1'='1", password: "x"}
Expected: 401 Unauthorized (handled safely)
Verify: No users leaked
TC007: Case Sensitivity 🔤
Input: {email: "John@Ex.Com", password: "Pass@123"}
Expected: 200 OK (emails are case-insensitive)
Verify: Login works
TC008: Whitespace Trimming 🔲
Input: {email: " john@ex.com ", password: " Pass@123 "}
Expected: 200 OK (trimmed)
Verify: Login works
TC009: Rate Limiting 🚫
Send 10 login requests in 1 second
Expected: After 5th request → 429 Too Many Requests
Verify: Retry-After header present
TC010: Account Disabled 🔒
Input: {email: "disabled@ex.com", password: "Pass@123"}
Expected: 403 Forbidden
Verify: Appropriate error message
🔊 "Nhìn 10 test cases này, bạn thấy từ 1 endpoint (login), mình tạo ra 30+ test cases! Đó là comprehensive testing. Mỗi test case cover một scenario khác nhau: happy path (TC001), wrong password (TC002), missing field (TC004), SQL injection (TC006), rate limiting (TC009), etc. Đây là cách tôi làm việc trong 50+ projects."

🗄️ Database Verification (Critical!)

🚨 Important Principle:

NEVER trust API 201 response alone!

✅ API returns 201 Created
✅ Response contains user id, name, email
❌ But data NOT saved in database!

→ Only database testing catches this!

📌 Example: Verify POST /api/users Creates User in DB

Step 1: Prepare -- Get users count BEFORE SELECT COUNT(*) FROM users Step 2: Act POST /api/users {"name": "Jane", "email": "jane@ex.com"} Response: 201 Created, {"id": 100, ...} Step 3: Verify API Response - Status = 201 ✓ - Response.id exists ✓ - Response.name = "Jane" ✓ Step 4: Verify Database (CRITICAL!) SELECT * FROM users WHERE id = 100 → Row exists? ✓ → name = "Jane"? ✓ → email = "jane@ex.com"? ✓ → created_at is timestamp? ✓ Step 5: Cleanup DELETE FROM users WHERE id = 100

🎯 Why Database Verification?

  • ✓ API response can lie (return data not actually saved)
  • ✓ Verify end-to-end: API → Business Logic → Database
  • ✓ Catch bugs in ORM, transactions, constraints
  • ✓ Ensure data consistency
🔊 "Đây là kinh nghiệm từ 50+ projects của tôi: một lần, API trả về 201 Created, response có user id, name, email. Mình think 'ok task done'. Nhưng khi check database... không có user đó! Cơ sở dữ liệu empty! Bug này là transaction rollback lúc save. Nếu mình không verify database, bug này sẽ go to production. Users sign up, không thấy account, complain, lose trust. Catastrophic!"

🎓 Interview Preparation

🔥 Top 10 Interview Questions (Likely to Ask):

Q1: What's the difference between 401 and 403?

✅ Correct Answer:
"401 Unauthorized = authentication failed (prove who you are)
403 Forbidden = authenticated but no permission (I know you, but you can't access)"

❌ Wrong Answer: "Same thing"
Q2: How do you test an API endpoint that creates a resource?

✅ Correct Answer:
"1) Happy path (create → 201)
2) Negative (invalid input → 400)
3) Database verify (check DB, row exists)
4) Idempotency test (retry same call)
5) Security test (SQL injection, bypass)"

❌ Wrong Answer: "Just check if response is 201"
Q3: What is idempotency and why does it matter?

✅ Correct Answer:
"Idempotent = calling 1x or 100x = same result
GET, PUT, DELETE idempotent (safe retry)
POST, PATCH not (risk duplicates)
For payment/order: MUST test idempotency"
Q4: Why is database verification important?

✅ Correct Answer:
"API response can lie. Example: API returns 201, data structure looks correct, but NOT saved in DB. Only DB query catches this. Never trust API response alone."
Q5: REST vs SOAP, which is better?

✅ Correct Answer:
"REST simple, stateless, cacheable, 80% use (better)
SOAP complex, secure, enterprise (specific use)
Context matters: startup use REST, bank use SOAP"

💡 Pro Tips for Interview:

  • ✨ Use real examples from projects you worked on
  • ✨ Emphasize: "I always test at 3 levels: API response, DB state, side effects"
  • ✨ Mention security testing as part of test design
  • ✨ Talk about database verification (impress them!)
  • ✨ Understand idempotency concept deeply
  • ✨ Know the difference between 401/403/404 perfectly
🔊 "Nếu bạn được hỏi những câu hỏi này ở interview, hãy trả lời tự tin. Nếu bạn nói 'I always verify database after POST create' - recruiter sẽ impress! Vì 90% testers chỉ check API response, không check DB. But you do - và đó là reason bạn catch more bugs!"
