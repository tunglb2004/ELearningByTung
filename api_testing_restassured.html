🔧 Setup RestAssured Project từ 0

STEP 1: Tạo Maven Project

Maven là build tool cho Java. Nó manage dependencies (thư viện), compile code, chạy tests.

mkdir api-testing-automation cd api-testing-automation mvn archetype:generate \ -DgroupId=com.qa \ -DartifactId=api-tests \ -DarchetypeArtifactId=maven-archetype-quickstart

STEP 2: Add Dependencies to pom.xml

pom.xml là file config Maven - nó định nghĩa dependencies (thư viện) project cần dùng.

<dependencies> <!-- RestAssured for API testing --> <dependency> <groupId>io.rest-assured</groupId> <artifactId>rest-assured</artifactId> <version>5.4.0</version> </dependency> <!-- TestNG for test execution --> <dependency> <groupId>org.testng</groupId> <artifactId>testng</artifactId> <version>7.8.1</version> <scope>test</scope> </dependency> <!-- JSON parsing --> <dependency> <groupId>com.fasterxml.jackson.core</groupId> <artifactId>jackson-databind</artifactId> <version>2.16.0</version> </dependency> </dependencies>

STEP 3: Project Structure

api-testing-automation/ ├── pom.xml ├── src/ │ ├── main/java/com/qa/ │ │ ├── config/ (Cấu hình base URL, timeout) │ │ ├── utils/ (Helper methods, utilities) │ │ ├── models/ (Request/Response POJOs) │ │ ├── api/ (API endpoints - Page Object) │ │ └── constants/ (Constants, enums) │ │ │ └── test/java/com/qa/ │ ├── tests/ (Actual test cases) │ ├── base/ (BaseTest class) │ ├── listeners/ (Test listeners for reporting) │ └── resources/ │ ├── testdata.json (Test data) │ └── config.properties (Configuration)

STEP 4: Chạy Maven Commands

# Compile & test mvn clean test # Run specific test class mvn test -Dtest=UserAPITest # Generate reports mvn allure:report allure serve target/allure-results
🔊 "Alright, bây giờ chúng ta setup project. Đừng sợ command line! Nó khó nhìn nhưng thực ra simple. Maven là gì? Maven là 'package manager' cho Java. Giống như npm cho Node, pip cho Python. Maven giúp manage dependencies (thư viện project cần), compile code, chạy tests. pom.xml là file config Maven. Nó nói: 'Hey Maven, project này cần dependencies nào?' Chúng ta define dependencies ở đây. Maven sẽ auto download từ internet. Dependencies chúng ta cần: 1. RestAssured 5.4.0 - main library cho API testing 2. TestNG 7.8.1 - test framework (alternative to JUnit) 3. Jackson 2.16.0 - JSON parsing library 4. SLF4J - logging Project structure rất important. Chúng ta separate concerns: - API objects ở folder 'api' (Page Object Model) - Test cases ở folder 'tests' - Test data ở folder 'resources' - Utilities & helpers ở folder 'utils' Tại sao? Vì clean code = maintainable code = easy to scale. Maven commands: - `mvn clean test` = delete old build, compile, run tests - `mvn clean test -Dtest=UserAPITest` = run specific test class - `mvn allure:report` = generate beautiful report Setup này mất 1 giờ lần đầu. Sau đó, mỗi project mới chỉ copy paste pom.xml. Done."

📝 RestAssured Basic Syntax - Hello World

RestAssured Pattern: Given-When-Then (BDD)

RestAssured dùng Fluent Interface - cú pháp giống English, dễ đọc.

Ví Dụ 1: Simple GET Request

import static io.rest_assured.RestAssured.*; import org.testng.annotations.Test; public class UserAPITest { @Test public void testSimpleGetRequest() { // Test GET /api/users endpoint given() // ARRANGE: Chuẩn bị (setup URL, headers, params) .baseUri("https://jsonplaceholder.typicode.com") .basePath("/users") .when() // ACT: Thực thi (gửi request) .get() .then() // ASSERT: Verify (check response) .statusCode(200) .body("size()", greaterThan(0)); } }

Giải Thích Pattern:

given() = Chuẩn bị setup

  • .baseUri() = Base URL (https://api.example.com)
  • .basePath() = Path (/users, /products)
  • .header() = HTTP headers
  • .queryParam() = Query parameters
  • .body() = Request body (POST, PUT)

when() = Thực thi HTTP request

  • .get() = GET request
  • .post() = POST request
  • .put() = PUT request
  • .delete() = DELETE request

then() = Kiểm tra response

  • .statusCode(200) = Check HTTP status
  • .body("path", matcher) = Check response body
  • .header("Content-Type", containsString("json")) = Check headers

Output Khi Chạy Test:

# Test PASS: Tests run: 1, Failures: 0, Skipped: 0, Time: 1.234s ✅ # Test FAIL: Tests run: 1, Failures: 1, Skipped: 0 AssertionError: expected status code <200> but was <404>
🔊 "Đây là 'Hello World' của RestAssured. Rất simple. given-when-then là BDD pattern (Behavior Driven Development). Nó make code readable - một tester non-technical cũng có thể hiểu. given() = Chuẩn bị. Bạn nói với RestAssured: 'Tôi muốn test cái gì? Với URL nào? Header nào?' when() = Hành động. Bạn gửi request: GET /users then() = Kiểm tra. Bạn check: Response trả về status 200 chưa? Response body có dữ liệu chưa? baseUri = Base URL (https://api.example.com) basePath = Path (/users) Combine = https://api.example.com/users statusCode(200) = HTTP status code phải là 200 (OK). Nếu là 404 (Not Found), test fail. .body(\"size()\", greaterThan(0)) = Response array phải có size > 0 (có ít nhất 1 user). Cú pháp `\"size()\"` là JSONPath - để extract dữ liệu từ JSON response. Xong, chúng ta chạy `mvn clean test` - test sẽ run. Pass or Fail. Done!"

📝 GET Request với Query Parameters

Ví Dụ: GET /api/users?status=active&limit=10

@Test public void testGetUsersWithFilters() { given() .baseUri("https://api.example.com") .basePath("/users") .queryParam("status", "active") .queryParam("limit", 10) .queryParam("page", 1) .when() .get() .then() .statusCode(200) .body("data.size()", equalTo(10)) .body("data[0].status", equalTo("active")) .body("data[0].id", notNullValue()); }

Giải Thích:

.queryParam("status", "active") = Thêm query parameter

Kết quả URL: https://api.example.com/users?status=active&limit=10&page=1

.body("data.size()", equalTo(10)) = Check response array 'data' có size = 10

.body("data[0].status", equalTo("active")) = Check phần tử đầu tiên, field 'status' = "active"

Response JSON Example:

{ "data": [ { "id": 1, "name": "John", "status": "active" }, { "id": 2, "name": "Jane", "status": "active" }, ... ], "total": 10 }

Common Matchers:

equalTo(value) - bằng nhau

notNullValue() - không null

containsString("text") - chứa text

greaterThan(5) - lớn hơn 5

lessThan(10) - nhỏ hơn 10

hasItems(item1, item2) - array chứa items

🔊 "Bây giờ chúng ta add query parameters. Query parameters là '?status=active&limit=10' - tham số truyền ở URL. .queryParam() method thêm query parameter. JSONPath là khái niệm important. Để extract dữ liệu từ JSON response, chúng ta dùng JSONPath syntax: - \"size()\" = array size - \"[0]\" = phần tử đầu tiên - \"data[0].status\" = first user's status Matchers là tools để compare values: - equalTo(value) = exact match - containsString() = substring match - greaterThan() = numeric comparison So chúng ta test: 1. Status code = 200 (OK) 2. Array size = 10 3. First user status = 'active' 4. First user id không null Nếu bất kỳ assertion nào fail, test fail. That's how automation works."

📝 POST Request - Create Resource

Ví Dụ 1: POST với String Body

@Test public void testCreateUser() { String requestBody = """ { "name": "John Doe", "email": "john@example.com", "password": "SecurePass@123", "role": "user" } """; given() .baseUri("https://api.example.com") .basePath("/users") .contentType("application/json") .body(requestBody) .when() .post() .then() .statusCode(201) // 201 Created .body("id", notNullValue()) .body("name", equalTo("John Doe")) .body("email", equalTo("john@example.com")); }

Ví Dụ 2: POST với Map (Cleaner)

@Test public void testCreateUserWithMap() { Map<String, Object> requestBody = new HashMap<>(); requestBody.put("name", "John Doe"); requestBody.put("email", "john@example.com"); requestBody.put("password", "SecurePass@123"); given() .baseUri("https://api.example.com") .basePath("/users") .contentType("application/json") .body(requestBody) .when() .post() .then() .statusCode(201) .body("id", notNullValue()); }

Important: HTTP Status Codes

Code Meaning Khi Nào
200 OK GET request thành công
201 Created POST request tạo resource thành công
204 No Content DELETE request thành công (no response body)
400 Bad Request Request data invalid (missing fields, wrong format)
401 Unauthorized Không có authentication (quên token)
403 Forbidden Không có quyền (wrong role)
404 Not Found Resource không tồn tại
500 Internal Server Error Server error (bug ở backend)
🔊 "POST request = tạo resource mới. Ví dụ tạo user mới ở API. .contentType(\"application/json\") = nói với server: 'Tôi gửi JSON data'. Server sẽ hiểu. .body() = request body. Có 2 cách: 1. String: \"{ \\\"name\\\": \\\"John\\\" }\" 2. Map: requestBody.put(\"name\", \"John\") Mình recommend Map - cleaner, easier to maintain. statusCode(201) = HTTP 201 Created. Nếu server trả về 200 or 400, test fail. HTTP Status Codes rất important: - 2xx = Success (200, 201, 204) - 4xx = Client error (400, 401, 403, 404) - 5xx = Server error (500) Ví dụ: - POST create user successful = 201 - POST with missing email = 400 (bad request) - DELETE user without auth token = 401 (unauthorized) - DELETE user with wrong role = 403 (forbidden) Good API test phải test cả happy path (success) lẫn error cases (failures). We'll talk more about this later."

📝 PUT & DELETE Requests

PUT Request - Update Resource

@Test public void testUpdateUser() { Map<String, Object> updateBody = new HashMap<>(); updateBody.put("name", "Jane Doe"); updateBody.put("email", "jane@example.com"); given() .baseUri("https://api.example.com") .basePath("/users") .pathParam("id", 123) .contentType("application/json") .body(updateBody) .when() .put("/{id}") .then() .statusCode(200) .body("name", equalTo("Jane Doe")) .body("email", equalTo("jane@example.com")); }

DELETE Request

@Test public void testDeleteUser() { given() .baseUri("https://api.example.com") .basePath("/users") .pathParam("id", 123) .when() .delete("/{id}") .then() .statusCode(204); // No content returned }

Giải Thích Path Parameters:

.pathParam("id", 123) = định nghĩa path parameter

.put("/{id}") = dùng path parameter trong URL

Kết quả: https://api.example.com/users/123

Toàn Bộ CRUD Operations:

Operation HTTP Method URL Status Code
Create POST /users 201
Read GET /users/123 200
Update PUT /users/123 200
Delete DELETE /users/123 204
🔊 "PUT = update resource. .pathParam() = path parameter. Dùng khi cần truyền ID hoặc identifier ở URL. Ví dụ: PUT /users/{id} - chúng ta muốn update user với ID = 123. .pathParam(\"id\", 123) nói: 'Replace {id} with 123' Kết quả: PUT /users/123 DELETE = xóa resource. DELETE /users/123 = xóa user với ID 123. Status code 204 = No Content. Server xóa thành công, không return data. Test chỉ check status = 204, không check body (vì không có body). CRUD = Create, Read, Update, Delete - CREATE = POST /users (201) - READ = GET /users/123 (200) - UPDATE = PUT /users/123 (200) - DELETE = DELETE /users/123 (204) Đây là standard REST API pattern. Mỗi API phải follow này (hoặc similar)."

🔐 Authentication & Request Headers

ví Dụ: Bearer Token Authentication

@Test public void testWithAuthentication() { String token = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."; given() .baseUri("https://api.example.com") .basePath("/users/me") .header("Authorization", "Bearer " + token) .header("Accept", "application/json") .when() .get() .then() .statusCode(200) .body("id", notNullValue()); }

Better Approach: Get Token Từ Login

@Test public void testGetTokenAndUseIt() { // STEP 1: Login - get token String token = given() .baseUri("https://api.example.com") .basePath("/auth/login") .body(Map.of("email", "user@ex.com", "password", "pass")) .contentType("application/json") .when() .post() .then() .statusCode(200) .extract() .path("token"); // STEP 2: Use token to get user profile given() .baseUri("https://api.example.com") .basePath("/users/me") .header("Authorization", "Bearer " + token) .when() .get() .then() .statusCode(200) .body("id", notNullValue()); }

Giải Thích: extract()

.extract() = extract dữ liệu từ response để dùng sau

.path("token") = extract field 'token' từ response body

Token sau đó dùng để gửi request tiếp theo (authorization)

Common HTTP Headers:

Header Purpose Example
Authorization Authentication token Bearer eyJhbGc...
Content-Type Request body format application/json
Accept Expected response format application/json
X-API-Key API key for authentication abc123xyz
User-Agent Client identifier RestAssured/5.4
🔊 "Authentication rất important. 90% real-world APIs cần authentication. Token = credential . Sau khi user login, server trả về token. Token này prove: 'This request is from authenticated user'. .header() method thêm HTTP header. .header(\"Authorization\", \"Bearer \" + token) nói: 'Hey server, this request is from authenticated user with this token' Approach 1 = hardcode token. Cách nhanh nhưng không real. Untuk production test phải get token từ login API. Approach 2 = login first, extract token, use token. Real-world approach. .extract() = extract dữ liệu từ response. .extract().path(\"token\") = từ response JSON, extract field 'token'. Ví dụ response: { \"token\": \"abc123\", \"userId\": 1 } .path(\"token\") sẽ extract \"abc123\" Stateful testing = test1 output = test2 input. STEP 1: Login API → get token STEP 2: Use token → call profile API Ini common pattern dalam automation - especially dalam workflow testing."

📊 Response Extraction & Complex Assertions

Ví Dụ: Extract Multiple Values từ Response

@Test public void testExtractResponseData() { // Make request & extract multiple fields Response response = given() .baseUri("https://jsonplaceholder.typicode.com") .basePath("/users") .pathParam("id", 1) .when() .get("/{id}") .then() .statusCode(200) .extract() .response(); // Extract individual fields int userId = response.path("id"); String userName = response.path("name"); String userEmail = response.path("email"); String userPhone = response.path("phone"); // Use extracted data in logic System.out.println("User: " + userName + " - " + userEmail); Assert.assertTrue(userEmail.contains("@")); }

JSONPath Syntax Examples:

.path("name") → extract top-level field 'name'

.path("address.city") → nested object (address.city)

.path("items[0].id") → first item in array

.path("items.collect{it.id}") → extract all ids from array

Response Object Methods:

// Get response body as String String body = response.getBody().asString(); // Get response as JSON JsonPath jsonBody = response.jsonPath(); int id = jsonBody.getInt("id"); // Get specific header String contentType = response.getHeader("Content-Type"); // Get all headers Headers headers = response.getHeaders();

Advanced Assertions:

import static org.hamcrest.Matchers.*; given()... .then() // String assertions .body("email", containsString("@example.com")) .body("email", matchesPattern("^[\\w\\.-]+@example\\.com$")) // Collection assertions .body("items", hasSize(5)) .body("items.id", hasItems(1, 2, 3)) // Numeric assertions .body("age", greaterThanOrEqualTo(18)) .body("score", between(0, 100)) // Null/Empty assertions .body("id", notNullValue()) .body("errors", empty());
🔊 "Sekarang chúng ta talk about complex assertions - không chỉ check status code mà check response data carefully. .extract() = powerful. Sau response, chúng ta bisa extract individual fields và dùng dalam logic. Contoh: 1. POST create user → extract userId 2. Use userId → call GET /users/{id} 3. Verify user details Response object = response dari API. Kita bisa extract: - Body as String - Body as JSON (JsonPath) - Headers - Status code JSONPath adalah powerful. Think of it as 'XPath for JSON'. - \"name\" = top-level field - \"address.city\" = nested (address object → city field) - \"[0]\" = array index - \"items[0].id\" = first item → id field Hamcrest Matchers = library untuk complex assertions. - containsString() = substring match - hasSize() = array/list size - greaterThan() = numeric comparison - matchesPattern() = regex match Why use these? Because simple assertion tidak cukup. Kita perlu: - Verify email format (regex) - Check array memiliki exact items - Check number dalam range - Check data tidak null/empty Professional automation berarti detailed assertions, bukan hanya status code."

🏗️ Page Object Model (POM) for APIs

Kenapa POM?

Problem: Test code menjadi messy jika semua API calls langsung di test class

Solution: Pisahkan API objects dari test logic

STEP 1: Buat API Object Class

public class UserAPI { private static final String BASE_URL = "https://api.example.com"; private static final String USER_ENDPOINT = "/users"; private RequestSpecification spec; private Response response; public UserAPI() { this.spec = given() .baseUri(BASE_URL) .basePath(USER_ENDPOINT) .contentType("application/json"); } // Get all users public UserAPI getAllUsers() { this.response = spec.when().get(); return this; } // Get user by ID public UserAPI getUserById(int userId) { this.response = spec .pathParam("id", userId) .when() .get("/{id}"); return this; } // Create user public UserAPI createUser(Map<String, Object> userData) { this.response = spec .body(userData) .when() .post(); return this; } // Assertions public UserAPI statusCodeShouldBe(int expectedCode) { response.then().statusCode(expectedCode); return this; } public UserAPI nameEqualsTo(String expectedName) { response.then().body("name", equalTo(expectedName)); return this; } // Get response data public int getUserId() { return response.path("id"); } }

STEP 2: Clean Test Class dengan POM

public class UserAPITest { private UserAPI userAPI; @BeforeMethod public void setup() { userAPI = new UserAPI(); } @Test public void testGetAllUsers() { userAPI.getAllUsers() .statusCodeShouldBe(200); } @Test public void testCreateAndGetUser() { // Create user userAPI.createUser(Map.of( "name", "John", "email", "john@ex.com" )) .statusCodeShouldBe(201); // Get created user ID int userId = userAPI.getUserId(); // Get user details userAPI.getUserById(userId) .statusCodeShouldBe(200) .nameEqualsTo("John"); } }

Benefits:

✅ Readability: Test methods jadi sangat clean dan readable

✅ Reusability: Banyak tests bisa reuse API methods

✅ Maintainability: API change? Update UserAPI class sahaja, tests tetap sama

✅ Scalability: Mudah add endpoint baru

🔊 "POM = Page Object Model - sebenarnya adalah pattern untuk separate concerns. Problem tanpa POM: Setiap test class full dengan given-when-then code. API call logic tersebar di test. Jika API change (URL, headers, params), harus update semua tests. Maintenance nightmare. Solution dengan POM: Buat API object class (UserAPI, ProductAPI). Semua API calls ada di class ini. Test class hanya call methods dari API object. Clean, readable, maintainable. UserAPI class: - Define base URL & endpoints - Create RequestSpecification (reusable setup) - Methods untuk operations: getAllUsers(), getUserById(), createUser() - Methods untuk assertions: statusCodeShouldBe(), nameEqualsTo() - Methods untuk extract: getUserId() Fluent interface pattern: Setiap method return 'this', jadi bisa chain methods. .createUser(...).statusCodeShouldBe(201).nameEqualsTo(\"John\") Test class dengan POM: Sangat clean! Tidak ada given-when-then detail, hanya business logic. Advantage: - API URL change? Update UserAPI, tests automatic ok - Add new header? Update spec di UserAPI - New endpoint? Add method ke UserAPI - Tests don't care - mereka hanya call methods Ini adalah professional automation pattern. Besar projects semua use ini."

🧪 TestNG Framework Basics

TestNG vs JUnit

Feature JUnit TestNG
Setup/Teardown @Before/@After @BeforeMethod/@AfterMethod
Class-level setup @BeforeClass/@AfterClass @BeforeClass/@AfterClass
Data-driven tests Parameterized (kompleks) @DataProvider (simple)
Test groups ❌ No ✅ @Test(groups={"smoke"})
Priority ❌ No ✅ @Test(priority=1)
Soft Assertions ❌ No ✅ SoftAssert
Parallel execution ❌ Kompleks ✅ Simple (XML config)

TestNG Annotations:

public class UserAPITest { // Run ONCE before ALL tests in class @BeforeClass public void setupClass() { System.out.println("Setup class - run ONCE"); } // Run BEFORE EACH test @BeforeMethod public void setupMethod() { System.out.println("Setup method - run before each test"); } // ACTUAL TEST @Test(priority=1, groups={"smoke"}) public void testGetAllUsers() { System.out.println("Test get all users"); } @Test(priority=2) public void testCreateUser() { System.out.println("Test create user"); } // Run AFTER EACH test @AfterMethod public void teardownMethod() { System.out.println("Teardown method - cleanup"); } // Run ONCE after ALL tests @AfterClass public void teardownClass() { System.out.println("Teardown class"); } }

Execution Order:

@BeforeClass → run ONCE ↓ @BeforeMethod → run before test1 Test1 @AfterMethod → run after test1 ↓ @BeforeMethod → run before test2 Test2 @AfterMethod → run after test2 ↓ @AfterClass → run ONCE

Hard Assert vs Soft Assert:

// HARD ASSERT - fail immediately @Test public void testWithHardAssert() { Assert.assertEquals(actual, expected); // Fail? Stop here Assert.assertTrue(condition); // Won't run if above fails } // SOFT ASSERT - collect all failures @Test public void testWithSoftAssert() { SoftAssert softAssert = new SoftAssert(); softAssert.assertEquals(actual1, expected1); softAssert.assertEquals(actual2, expected2); softAssert.assertTrue(condition); softAssert.assertAll(); // Fail at end if any failed }
🔊 "TestNG adalah test framework untuk Java. Seperti JUnit, tapi lebih powerful. @BeforeClass = setup satu kali sebelum semua tests di class. Contoh: setup database, read configuration @BeforeMethod = setup sebelum SETIAP test. Contoh: reset data, login user @Test = actual test case. Ini yang dijalankan oleh TestNG. Priority = order of execution. priority=1 run dulu, priority=2 kemudian. Groups = kategorisasi tests. @Test(groups={\"smoke\"}) = test ini bagian dari 'smoke' group Mengapa? Jadi kita bisa run subset of tests. mvn test -Dgroups=smoke = run hanya smoke tests (2 menit) mvn test -Dgroups=regression = run semua tests (30 menit) Hard Assert = fail immediately. Test stop. Next assertion tidak run. Soft Assert = collect semua failures, report at end. Better untuk detailed bug reports. Contoh: POST create user dengan missing fields. Hard assert: fail di field 1 check, tidak check field 2-5 Soft assert: check semua fields, report semua failures @AfterMethod</strong = cleanup setelah SETIAP test. Contoh: delete created data, logout user Ini very important untuk test isolation - setiap test independent, tidak affect test lain."

📊 Data-Driven Testing dengan @DataProvider

Apa itu Data-Driven Testing?

Satu test method, banyak data sets. Contoh: testCreateUser dengan 10 user data - run 10 kali dengan data berbeda.

Benefit: Reduce code duplication, test banyak scenarios dengan satu method

Ví Dụ 1: Simple @DataProvider

public class UserAPITest { // Data provider - return test data @DataProvider(name="userDataProvider") public Object[][] provideUserData() { return new Object[][] { { "John Doe", "john@ex.com" }, { "Jane Smith", "jane@ex.com" }, { "Bob Wilson", "bob@ex.com" }, { "Alice Brown", "alice@ex.com" } }; } // Test with data provider @Test(dataProvider="userDataProvider") public void testCreateUserMultipleScenarios( String name, String email) { Map<String, Object> userData = Map.of( "name", name, "email", email ); userAPI.createUser(userData) .statusCodeShouldBe(201) .nameEqualsTo(name); } }

Result: 4 Tests Run dengan Satu Method

[TestNG] Running: Test 1: testCreateUserMultipleScenarios(John Doe, john@ex.com) ✅ Test 2: testCreateUserMultipleScenarios(Jane Smith, jane@ex.com) ✅ Test 3: testCreateUserMultipleScenarios(Bob Wilson, bob@ex.com) ✅ Test 4: testCreateUserMultipleScenarios(Alice Brown, alice@ex.com) ✅ Tests run: 4, Failures: 0 ✅

Ví Dụ 2: Complex Data Objects

// Custom data class class UserTestData { public String name, email, phone, role; public int expectedStatusCode; public UserTestData(String name, String email, String phone, String role, int expectedStatusCode) { this.name = name; this.email = email; this.phone = phone; this.role = role; this.expectedStatusCode = expectedStatusCode; } } // Data provider with objects @DataProvider public Object[][] provideComplexUserData() { return new Object[][] { { new UserTestData("John", "john@ex.com", "123456", "user", 201) }, { new UserTestData("Jane", "invalid-email", "123456", "user", 400) }, { new UserTestData("Bob", "bob@ex.com", "123456", "admin", 201) } }; } @Test(dataProvider="provideComplexUserData") public void testWithComplexData(UserTestData testData) { Map<String, Object> userData = Map.of( "name", testData.name, "email", testData.email, "phone", testData.phone, "role", testData.role ); userAPI.createUser(userData) .statusCodeShouldBe(testData.expectedStatusCode); }
🔊 "Data-driven testing = parameterized testing. Satu method, banyak data. @DataProvider = return test data. Method ini return 2D array Object[][]. Setiap row = satu test case. Contoh: return new Object[][] { { \"John\", \"john@ex.com\" }, ← Test case 1 { \"Jane\", \"jane@ex.com\" } ← Test case 2 } TestNG akan run testCreateUserMultipleScenarios 2 kali: 1st run dengan (\"John\", \"john@ex.com\") 2nd run dengan (\"Jane\", \"jane@ex.com\") Benefit: 1. Reduce code duplication - tidak perlu 4 methods, 1 method with 4 data sets 2. Easy to add more data - edit DataProvider array 3. Clear test intent - \"test create user with these 4 scenarios\" Complex data: Jika data complex (multiple fields, conditions), buat custom class (UserTestData). Return objects dari DataProvider. Real-world example: Test login dengan 5 invalid passwords, 10 valid emails, 20 password edge cases. Bukan 20 methods - 20 data rows, 1 method! Ini powerful untuk boundary testing, edge cases, negative testing. We'll use this extensively later."

🔧 BaseTest Class & Configuration Management

Why BaseTest?

Setiap test class punya setup/teardown yang sama - initialization, cleanup, etc.

Daripada repeat code, buat BaseTest - parent class dengan shared logic.

BaseTest Class Implementation:

public class BaseTest { protected UserAPI userAPI; protected ProductAPI productAPI; protected OrderAPI orderAPI; protected String authToken; protected int testUserId; // Load configuration from properties file protected static String BASE_URL; protected static String API_KEY; protected static String TEST_EMAIL; protected static String TEST_PASSWORD; @BeforeClass public static void loadConfig() { Properties props = new Properties(); try { props.load(new FileInputStream( "src/test/resources/config.properties")); } catch (IOException e) { e.printStackTrace(); } BASE_URL = props.getProperty("base.url"); API_KEY = props.getProperty("api.key"); TEST_EMAIL = props.getProperty("test.email"); TEST_PASSWORD = props.getProperty("test.password"); } @BeforeMethod public void setUp() { // Initialize API objects userAPI = new UserAPI(BASE_URL, API_KEY); productAPI = new ProductAPI(BASE_URL, API_KEY); orderAPI = new OrderAPI(BASE_URL, API_KEY); // Login & get token authToken = userAPI.login(TEST_EMAIL, TEST_PASSWORD); } @AfterMethod public void tearDown() { // Cleanup after test if (testUserId > 0) { userAPI.deleteUser(testUserId); } } }

Test Class Extending BaseTest:

public class UserAPITest extends BaseTest { @Test public void testGetAllUsers() { // userAPI, authToken sudah available dari BaseTest userAPI.getAllUsers() .statusCodeShouldBe(200); } @Test public void testCreateUser() { // No setup needed, BaseTest setup sudah run userAPI.createUser(Map.of( "name", "Test User", "email", "test@ex.com" )) .statusCodeShouldBe(201); } }

Configuration File (config.properties):

# Base URL base.url=https://api.example.com # API credentials api.key=sk_test_abc123xyz # Test data test.email=qa@example.com test.password=SecurePass@123 # Timeout (ms) request.timeout=10000 response.timeout=10000 # Logging log.level=INFO log.file=logs/test.log

Benefits:

✅ DRY (Don't Repeat Yourself): Setup code shared across all test classes

✅ Configuration: URL, credentials centralized - easy to switch dev/staging/prod

✅ Maintenance: Change setup logic once, all tests benefit

✅ Reusability: New test class just extends BaseTest

🔊 "BaseTest adalah pattern untuk share common logic across test classes. Imagine 10 test classes. Setiap kelas punya: - Initialize API objects - Load configuration - Login user - Cleanup Repeat code 10 kali? No! Buat BaseTest, extend dari situ. BaseTest punya: 1. Protected API objects (userAPI, productAPI, orderAPI) 2. Configuration loading (BASE_URL, API_KEY) 3. Setup logic (@BeforeMethod) 4. Teardown logic (@AfterMethod) Test classes extend BaseTest, inherit semua ini. Configuration file (properties): External, tidak hardcode. base.url=https://api.example.com Ngapa? Soalnya environment berbeda (dev, staging, prod) punya URL berbeda. Development: https://api.dev.example.com Staging: https://api.staging.example.com Production: https://api.example.com Jadi, same test code, change properties file = test against different environment. Test isolation: Setiap test @BeforeMethod run, @AfterMethod cleanup. Contoh: Test create user, teardown delete user. Next test start dengan clean state. Professional automation semua use ini pattern. If you master ini, banyak project siap accept you."
