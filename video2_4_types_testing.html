Và nếu bạn cố divide cho 0, nó có throw exception không? Đó chính là lúc bạn viết unit tests."

🧩 Unit Testing - Định Nghĩa

Unit là gì?

"Unit" = đơn vị nhỏ nhất trong code → thường là một method/function

Unit Testing là gì?

Unit Testing = Test từng method riêng lẻ, độc lập với các thành phần khác

Đặc Điểm

  • ✅ NHANH: Test chạy cực nhanh (milliseconds)
  • ✅ ĐỘC LẬP: Không cần database, browser, network
  • ✅ TẬP TRUNG: Chỉ test logic của 1 method
  • ✅ EASY DEBUG: Dễ tìm lỗi vì scope nhỏ
  • 🎯 NÊN VIẾT: 70% của tất cả tests

Ví Dụ

Có method: add(5, 3)

Unit test: assert add(5, 3) == 8 ✅

🔊 "Hãy xem code để test add() method. Đầu tiên, trong phần ARRANGE, tôi tạo một instance mới của Calculator bằng cách gọi new Calculator(). Tại sao? Vì tôi cần một object để gọi method add() trên nó. Tiếp theo, trong phần ACT, tôi gọi calc.add() với 2 parameters là 5 và 3, và lưu kết quả vào biến result. Tại sao? Vì tôi muốn lấy kết quả của method để so sánh. Cuối cùng, trong phần ASSERT, tôi sử dụng assertEquals() để so sánh expected value là 8 với actual value là result. Nếu 8 bằng result, test sẽ PASS. Nếu không bằng, test sẽ FAIL. Đó gọi là AAA pattern - Arrange, Act, Assert, một pattern rất phổ biến để viết unit tests. Bây giờ hãy xem test cho divide() method. Khi b bằng 0, method này sẽ throw một IllegalArgumentException. Làm cách nào để kiểm tra nó throw exception? Tôi sử dụng @Test(expected = IllegalArgumentException.class). Nó có ý là 'tôi kỳ vọng method này sẽ throw IllegalArgumentException'. Nếu method thực sự throw exception đó, test sẽ PASS. Nếu nó không throw hay throw một exception khác, test sẽ FAIL."

🧩 Unit Testing - Code Example

Calculator Class (Code cần test)

public class Calculator { public int add(int a, int b) { return a + b; } public int divide(int a, int b) { if (b == 0) { throw new IllegalArgumentException( "Cannot divide by zero" ); } return a / b; } }

Unit Tests (Code để test)

public class CalculatorTest { // Test add() với 2 số dương @Test public void testAddPositive() { Calculator calc = new Calculator(); int result = calc.add(5, 3); // Kiểm tra: result == 8? assertEquals(8, result); // ✅ PASS } // Test divide() khi chia cho 0 @Test(expected = IllegalArgumentException.class) public void testDivideByZero() { Calculator calc = new Calculator(); calc.divide(10, 0); // Sẽ throw exception ✅ } }
OUTPUT: Test 1: testAddPositive Input: add(5, 3) Expected: 8 Actual: 8 ✅ PASS Test 2: testDivideByZero Input: divide(10, 0) Expected: IllegalArgumentException Actual: Exception thrown ✅ PASS Total: 2 tests, 2 passed, 0 failed Time: 45ms ⚡
🔊 "Tại sao unit testing lại quan trọng? Thứ nhất, nó NHANH. Không cần browser, không cần database, không cần network. Test 100 unit tests chỉ mất 1 giây, so với manual test là 5 phút nhân 100 bằng 500 phút. Thứ hai, DỄ DEBUG. Nếu testAddPositive fail, bạn biết ngay lỗi là ở method add(), không cần kiểm tra cả hệ thống. Thứ ba, theo best practice, 70% của tất cả tests nên là unit tests vì nó fast, nên bạn có thể chạy nó thường xuyên, mỗi khi developers commit code. Thay vì @Test(expected = IllegalArgumentException.class), bạn có thể dùng assertThrows() method từ Java 8 trở lên. Cách này modern hơn và dễ đọc hơn. Bạn cũng có thể dùng try-catch kiểu cũ, nhưng nó verbose hơn. Có nhiều loại assertion khác mà bạn có thể dùng như assertEquals() để kiểm tra bằng nhau, assertNotEquals() để kiểm tra không bằng, assertTrue() và assertFalse() để kiểm tra boolean, assertNull() và assertNotNull() để kiểm tra null, và assertArrayEquals() để kiểm tra arrays."

⚙️ Integration Testing - Định Nghĩa

"Integration" = Hợp Nhất

Integration Testing = Test khi 2+ modules hoạt động cùng nhau

Khác Biệt vs Unit Test

  • Unit: Test 1 method → add(5,3)=8
  • Integration: Test 2-3 services + database → user created → account created → verified ✅

Đặc Điểm

  • ⏰ CHẬM HƠN: 500ms/test (phải I/O database)
  • ✅ CÓ DATABASE: Lưu/lấy từ database thực
  • ✅ CÓ API: Gọi external APIs
  • 🔍 PHÁT HIỆN: Bugs khi modules tương tác
  • 🎯 NÊN VIẾT: 20% của tất cả tests
🔊 "Loại thứ hai là INTEGRATION TESTING. Integration có nghĩa là hợp nhất. INTEGRATION TESTING là test khi 2 hay nhiều modules hoạt động cùng nhau. Lý do là gì? Ở unit testing, chúng ta test add() method riêng lẻ, test divide() riêng lẻ, nhưng chúng ta không biết liệu khi kết hợp chúng lại có work không. Hãy tưởng tượng một BankService mà sử dụng Calculator để tính toán số dư, sử dụng Database để lưu thông tin account, và sử dụng Logger để ghi lại giao dịch. Unit tests có thể pass cho mỗi method riêng lẻ, nhưng khi bạn gọi transferMoney() method, nó gọi calculate(), gọi database.save(), gọi logger.log(). Nếu bạn chỉ unit test, bạn không biết liệu database.save() có hoạt động không, liệu logger.log() có hoạt động không. Integration test sẽ giúp bạn kiểm tra tất cả những thứ này cùng nhau."

⚙️ Integration Testing - Ví Dụ

Scenario: Transfer Money (Transfer tiền)

Workflow: Get account A → Get account B → Transfer → Update DB

public class BankIntegrationTest { // Test: Transfer tiền thành công @Test public void testTransferMoney() { // Step 1: Chuẩn bị int accountAId = 1; int accountBId = 2; double amount = 1000; // Step 2: Get account A từ DB Account accountA = accountService.getAccountById(1); // accountA.balance = 5000 // Step 3: Get account B từ DB Account accountB = accountService.getAccountById(2); // accountB.balance = 5000 // Step 4: Transfer 1000 từ A → B boolean success = transactionService .transfer(accountAId, accountBId, amount); // Step 5: Verify kết quả assertTrue(success); // ✅ Transfer thành công? assertEquals(4000, accountA.getBalance()); // ✅ A = 4000? assertEquals(6000, accountB.getBalance()); // ✅ B = 6000? } }
OUTPUT: Test: testTransferMoney Step 1: Getting account A from DB Step 2: Getting account B from DB Step 3: Transferring 1000 from A to B Step 4: Updating DB for both accounts ✅ Transfer successful Assertions: ✅ Transfer should succeed: PASS ✅ Account A balance = 4000: PASS ✅ Account B balance = 6000: PASS Time: 523ms ⏱️
🔊 "Hãy xem code integration test cho BankService. Trong ARRANGE, tôi tạo 2 accounts với balance khác nhau. Account từ có 5000, account đến có 3000. Tôi save chúng vào test database, không phải database thực để không ảnh hưởng dữ liệu sản xuất. Tại sao test database? Vì database thực có dữ liệu sản xuất quan trọng. Trong ACT, tôi gọi bankService.transferMoney(1, 2, 1000) để transfer 1000 từ account 1 sang account 2. Trong ASSERT, tôi verify rằng balance của account 1 bây giờ là 4000 (5000 - 1000), balance của account 2 là 4000 (3000 + 1000). Tôi cũng verify rằng transaction được logged vào database. Nếu tất cả assertions pass, test sẽ PASS, điều này chứng tỏ rằng transferMoney() hoạt động đúng khi kết hợp calculator, database, và logger. Test thứ hai là negative test - test khi có lỗi. Tôi cố transfer 1000 từ account chỉ có 500. Nó sẽ throw InsufficientFundsException. Sau khi throw exception, balance không thay đổi - vẫn 500 và 3000. Đây là behavior mà integration test cần kiểm tra."

🌐 End-to-End (E2E) Testing - Định Nghĩa

"End-to-End" = Từ Đầu Đến Cuối

E2E Testing = Test toàn bộ user workflow từ lúc user bắt đầu đến khi hoàn thành task

Ví Dụ Workflow

  • 👤 User login
  • 🔍 Browse products
  • 🔎 Search product "Laptop"
  • 📦 Add to cart
  • 🛒 View cart
  • 💳 Checkout
  • 📝 Enter shipping info
  • 💰 Pay
  • ✅ See order confirmation

Đặc Điểm

  • 🐢 RẤT CHẬM: 20-30 seconds/test
  • 🌐 CẦN BROWSER: Chrome, Firefox, Safari (Selenium)
  • 👁️ USER PERSPECTIVE: Test từ browser, click, type
  • 🎯 NÊN VIẾT: 10% của tất cả tests
🔊 "Tại sao integration testing quan trọng? Thứ nhất, unit tests pass không có nghĩa là system works. Nếu chúng ta test unit riêng lẻ, mỗi cái pass, nhưng khi kết hợp lại có thể có problem với logic flow. Thứ hai, database integration. Unit tests không dùng database, nhưng integration tests dùng test database để verify read/write works. Thứ ba, error handling. Nếu database down, exception có được handle đúng không? Nếu logger fail, transfer có được cancel không? Tỷ lệ: 20% của tất cả tests nên là integration tests. Chúng chậm hơn unit tests vì cần I/O operations, nhưng quan trọng để verify components work together. Thay vì TestDatabase, bạn có thể dùng MOCKING - tạo fake objects. Với mocking library như Mockito, bạn dùng when() để mock behavior và verify() để kiểm tra method được gọi. Hoặc dùng EMBEDDED DATABASE như H2 hay SQLite - in-memory database chạy nhanh hơn external database."

🌐 E2E Testing - Ví Dụ Code

Shopping Workflow Test

🔊 "Loại thứ ba là E2E TESTING. E2E là viết tắt của End-to-End. E2E TESTING là test toàn bộ user journey từ lúc bắt đầu đến lúc hoàn thành task. Không test một method, không test một flow logic, mà test một workflow hoàn chỉnh của user. Ví dụ, bạn là một khách hàng trên Amazon, bạn muốn mua một laptop. Workflow của bạn sẽ là: mở website, login, search laptop, click vào product, xem chi tiết, configure options, add to cart, go to cart, verify product, checkout, enter address, enter payment, place order, xem confirmation. Đó là một E2E test - 19 bước! Unit test là test add() method, 1 dòng code, 1 giây. Integration test là test transferMoney(), 50 dòng code, 5 giây. E2E test là test toàn bộ shopping flow, 100+ dòng code, 20-30 giây vì phải mở browser, chờ pages load, chờ elements render."

📡 API Testing - Định Nghĩa

API = Application Programming Interface

API Testing = Test các API endpoints (GET, POST, PUT, DELETE) mà không cần browser

REST API Methods

  • GET /users/1 → Lấy user có ID=1
  • POST /users → Tạo user mới
  • PUT /users/1 → Update user ID=1
  • DELETE /users/1 → Xóa user ID=1

Đặc Điểm

  • ⚡ NHANH: 2-3 seconds/10 tests
  • ✅ KHÔNG CẦN UI: Chỉ gửi request, check response
  • ✅ DỄ MAINTAIN: Không phụ thuộc UI changes
  • 👨‍💻 BACKEND TESTING: Test backend APIs riêng biệt
  • 🎯 NÊN VIẾT: 20% của tất cả tests
🔊 "Code E2E test sẽ dài hơn. Tôi dùng Selenium WebDriver để tự động hóa browser. Đầu tiên tôi khởi tạo ChromeDriver - nó sẽ tự động mở Chrome. Tiếp theo tôi dùng driver.get() để điều hướng đến URL. Rồi tôi dùng driver.findElement() để tìm element bằng ID hay XPath, dùng sendKeys() để gõ text, dùng click() để click button, dùng getText() để lấy text. Tôi dùng WebDriverWait để chờ element xuất hiện - đây rất quan trọng vì page load không phải instantaneous. Cuối cùng tôi dùng assertTrue() hoặc assertEquals() để verify kết quả. E2E test này mô phỏng user thực sự mua hàng - từ login đến place order."

📡 API Testing - Ví Dụ Code

User API Tests

public class UserAPITest { // Test 1: GET /users/1 @Test public void testGetUser() { given() .baseUri("https://api.example.com") .when() .get("/users/1") .then() .statusCode(200) // Check status = 200 .body("name", equalTo("John")); } // Test 2: POST /users (Create new) @Test public void testCreateUser() { String body = "{\\"name\\":\\"Alice\\",\\"email\\":\\"alice@test\\"}"; given() .baseUri("https://api.example.com") .contentType("application/json") .body(body) .when() .post("/users") .then() .statusCode(201); // Check status = 201 Created } // Test 3: GET /users/999 (Not found) @Test public void testGetNonExistent() { given() .baseUri("https://api.example.com") .when() .get("/users/999") .then() .statusCode(404); // Check status = 404 } }
OUTPUT: Test 1: testGetUser Request: GET /users/1 Response Status: 200 OK ✅ Response Body: - id: 1 - name: John - email: john@example.com ✅ PASS Test 2: testCreateUser Request: POST /users Body: {"name":"Alice","email":"alice@test"} Response Status: 201 Created ✅ Response Body: {"id":11,"name":"Alice"} ✅ PASS Test 3: testGetNonExistent Request: GET /users/999 Response Status: 404 Not Found ✅ ✅ PASS Time: 2.3 seconds ⚡⚡
🔊 "Tại sao E2E test chậm? Vì nó phải khởi động browser (2 giây), mở website (3 giây), mỗi click hay type là 0.5-1 giây, chờ page load là 1-5 giây. Total là 20-30 giây cho 1 test. Nếu có 100 E2E tests, đó là 3000 giây = 50 phút = 1 giờ chỉ để run tests. Nếu developer thay 1 dòng code, họ phải chạy lại 1 giờ - không productive! Vì vậy chúng ta không thể chỉ dùng E2E tests. Chúng ta cần test pyramid. Thay vì Selenium, bạn có thể dùng Cypress hay Playwright - những tools này thường nhanh hơn Selenium. Puppeteer là một thay thế khác nếu bạn muốn tự động hóa browser theo low-level."

🔊 "Loại thứ tư là API TESTING. API là viết tắt của Application Programming Interface. API Testing là test API endpoints (GET, POST, PUT, DELETE) mà không cần browser hoặc UI. Tại sao? Vì user không tương tác trực tiếp với API, nhưng backend tương tác. Khi bạn click 'Add to Cart' button, browser gửi HTTP request đến server, server xử lý, server trả response. API testing sẽ test phần server này trực tiếp, bypass browser hoàn toàn. Ví dụ, API endpoint GET /users/1 sẽ trả JSON response với user info. POST /users sẽ tạo user mới. PUT /users/1 sẽ update user. DELETE /users/1 sẽ xóa user. API test sẽ verify status code, verify response body, verify headers."

🔺 Test Pyramid

Bao nhiêu % của mỗi loại test nên viết?

/\ / \ / 10%\ E2E Tests / E2E \ (20-30s each) /--------\ / 20% \ Integration Tests / Integration\ (0.5s each) / \ / 70% \ Unit Tests / Unit \ (ms each) \ / \-----------/

Lý Do:

  • ✅ Unit tests: Nhanh (ms) → Viết nhiều (70%)
  • ✅ Integration tests: Chậm (0.5s) → Viết vừa phải (20%)
  • ✅ E2E tests: Chậm lắm (20-30s) → Viết ít (10%)
  • ✅ API tests: Nhanh (ms) → Hoặc 20% hoặc kết hợp unit

Kết Quả: Chạy tất cả tests mất ~5 phút (fast feedback)

🔊 "Tôi dùng RestAssured library để test APIs. Syntax là given-when-then. Given() setup request - specify content type, body, headers. When() perform request - GET, POST, PUT, DELETE. Then() verify response - status code, body content. Ví dụ, GET /users/1 sẽ return status 200 với body chứa name 'John Doe', email chứa '@example.com', status 'active'. POST /users với body chứa new user info sẽ return status 201 Created với id không null. GET /users/9999 (non-existent user) sẽ return 404 Not Found. PUT /users/1 với updated info sẽ return 200 với updated data. DELETE /users/1 sẽ return 204 No Content. Mỗi test verify một aspect khác nhau của API."

🎯 Recap: 4 Loại Testing

1️⃣ Unit Testing

  • Test từng method riêng lẻ
  • Nhanh (ms), không cần database
  • 70% của tất cả tests

2️⃣ Integration Testing

  • Test 2+ modules hoạt động cùng nhau
  • Có database, có API
  • 20% của tất cả tests

3️⃣ E2E Testing

  • Test toàn bộ user workflow
  • Cần browser, chậm (20-30s)
  • 10% của tất cả tests

4️⃣ API Testing

  • Test backend APIs
  • Nhanh (ms), không cần browser
  • 20% của tất cả tests
🔊 "Bây giờ chúng ta đã học 4 loại tests: Unit, Integration, E2E, API. Câu hỏi là: chúng ta nên viết bao nhiêu tests cho mỗi loại? Nếu viết tất cả E2E, 180 tests nhân 30 giây = 1.5 giờ chỉ để run. Developers commit mỗi giờ - không productive! Giải pháp là TEST PYRAMID. Hình pyramid có 3 layer. Layer dưới cùng là UNIT TESTS 70% - test từng method, cực nhanh 1 giây per test. Layer giữa là INTEGRATION TESTS 20% - test modules cùng nhau, medium speed 5 giây per test. Layer trên cùng là E2E TESTS 10% - test user workflow, chậm 30 giây per test. Total time: 70% nhân 1 giây = 70 giây, 20% nhân 5 giây = 100 giây, 10% nhân 30 giây = 300 giây, total = 470 giây = 8 phút. Với 180 tests, mỗi commit triggers tests run 8 phút - acceptable! Developers có thể commit mỗi giờ mà vẫn productive. Vì vậy strategy là: viết nhiều unit tests (nhanh), viết vừa integration tests (medium), viết ít E2E tests (chậm). API tests không nằm trong pyramid nhưng cũng quan trọng - khoảng 20% giống integration tests."

🔊 "Kết luận là có 4 loại automation testing khác nhau, mỗi loại test một phần khác nhau. UNIT TESTS test từng method riêng lẻ - nhanh, cần nhiều. INTEGRATION TESTS test modules cùng nhau - medium speed, cần vừa. E2E TESTS test user workflows - chậm, cần ít. API TESTS test backend endpoints - nhanh, không cần browser. Strategy là follow test pyramid: 70% unit, 20% integration, 10% E2E, plus 20% API. Mỗi loại có ưu điểm: unit nhanh, integration test real integration, E2E test real user experience, API test backend. Chúng không thay thế nhau mà complement nhau. Một hệ thống kiểm thử tốt cần tất cả 4 loại. Trong video tiếp theo, chúng ta sẽ deep dive vào Selenium WebDriver - công cụ mà chúng ta dùng để tự động hóa browser cho E2E testing."
