🔑 Authentication vs Authorization

Khái Niệm Cơ Bản

Đây là concept MỤC TIÊU của buổi. Phải hiểu sâu. Rất nhiều engineers confuse hai cái này.

┌─────────────────────────────────────────────────────────────┐ │ AUTHENTICATION (Xác Thực - "WHO are you?") │ ├─────────────────────────────────────────────────────────────┤ │ ✓ Prove your identity │ │ ✓ Using credentials: username/password, token, biometric │ │ ✓ Example: Login → prove you're John, not someone else │ │ ✓ Once authenticated → server gives you TOKEN │ │ ✓ HTTP Response: 401 Unauthorized (if auth fails) │ │ ✓ Question: "Are you really John?" │ └─────────────────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────────────────┐ │ AUTHORIZATION (Phân Quyền - "What can you do?") │ ├─────────────────────────────────────────────────────────────┤ │ ✓ Check if authenticated user has permission │ │ ✓ Based on roles: admin, user, guest, moderator │ │ ✓ Example: John (user role) tries accessing /admin/reports │ │ ✓ Even if authenticated, may NOT be authorized │ │ ✓ HTTP Response: 403 Forbidden (if not authorized) │ │ ✓ Question: "Is John allowed to do this?" │ └─────────────────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────────────────┐ │ REAL WORLD ANALOGY (Dễ Hiểu) │ ├─────────────────────────────────────────────────────────────┤ │ Airport Security: │ │ │ │ Authentication: Officer checks your ID & passport │ │ "Bạn là John Smith không?" → "Có, đây là ID của tôi" │ │ │ │ Authorization: Officer looks at your visa/boarding pass │ │ "Bạn có phép bay đến New York không?" → "Có, đây là..." │ │ │ │ Result: │ │ - Authenticated ✓ + Authorized ✓ → Have access │ │ - Authenticated ✓ + NOT Authorized ✗ → No access (403) │ │ - NOT Authenticated ✗ → No access (401) │ └─────────────────────────────────────────────────────────────┘

401 vs 403 - Sự Khác Biệt Quan Trọng

HTTP Status Tên Gọi Ý Nghĩa Nguyên Nhân Ví Dụ
401 Unauthorized Xác thực thất bại Không có token, token sai, token hết hạn GET /api/users (no Authorization header)
403 Forbidden Không có quyền Đã authenticate nhưng không có permission GET /api/admin/logs (user role)
💡 Pro Tip: Khi testing, luôn kiểm tra:
  • 401 scenarios: Không có token, invalid token, expired token
  • 403 scenarios: Authenticated nhưng role không match
  • 200 scenarios: Authenticated & authorized ✓
🔊 "Okay, concept đầu tiên: Authentication vs Authorization. Cái này rất important vì 70% testers confuse hai concept này. Authentication - nó về IDENTITY . Câu hỏi là: 'WHO ARE YOU?'. Bạn prove rằng bạn là John bằng cách provide credentials - email/password. Server verify credentials, nếu đúng → give you token. Token này giống như ID card của bạn - prove bạn đã authenticate. Authorization - nó về PERMISSION . Câu hỏi là: 'WHAT CAN YOU DO?'. Bạn đã prove bạn là John. Nhưng can you access /admin/logs? Đó là authorization check. Server look at John's role - nếu user role, không có permission → 403 Forbidden. Real world example: Airport. Officer check ID (authentication) - 'bạn là John Smith không?' Bạn show ID. Officer verify, okay John bạn authenticate rồi. Nhưng sau đó officer check boarding pass (authorization). 'Bạn có phép fly to New York không?' Nếu boarding pass là New York, okay ✓ bạn authorized. Nếu boarding pass là Tokyo, sorry - 403 bạn không authorized. Result của hai concept này: - Authenticated ✓ + Authorized ✓ = 200 OK, access granted - NOT Authenticated ✗ = 401 Unauthorized, please login first - Authenticated ✓ nhưng NOT Authorized ✗ = 403 Forbidden, you can't access this Rất important distinguish 401 vs 403. Vì bugs often là ở 403 - authorization bypass. Attacker authenticate successful, nhưng bypass authorization."

Token Expiration & Refresh Flow

CLIENT REQUEST WITH EXPIRED TOKEN: GET /api/users/me Authorization: Bearer expired_token_3_days_ago SERVER VALIDATION: Parse token → Check expiration → EXPIRED! SERVER RESPONSE: HTTP 401 Unauthorized { "error": "Token expired", "error_code": "TOKEN_EXPIRED", "message": "Please refresh your token" } CLIENT REFRESH TOKEN: POST /api/auth/refresh { "refresh_token": "..." } SERVER GENERATES NEW TOKEN: HTTP 200 OK { "token": "new_jwt_token", "expiresIn": 3600 } CLIENT RETRIES WITH NEW TOKEN: GET /api/users/me Authorization: Bearer new_jwt_token → Success!
✅ Test Cases mỗi step:
  • Step 1: Test credentials validation (valid, invalid, missing)
  • Step 2: Test password hashing (must not be plaintext)
  • Step 3: Verify response contains token
  • Step 4: Verify client can store token
  • Step 5: Verify Authorization header format
  • Step 6: Verify token validation logic
  • Step 7: Verify user data returned correctly
🔊 "Ngay đây là authentication flow - quá quan trọng. Từ lúc user login cho đến lúc request data. Mỗi step đều là potential bug point. Step 1: Client send email + password. Simple. Nhưng test case ở đây: what if password wrong? Email không exist? Email null? These are our test cases. Step 2: Server validate. Very important step - nơi mà authentication logic nằm. Server check email exist. Then hash incoming password and compare with stored hash. WHY hash? Vì password tidak boleh disimpan plaintext. Ini adalah security requirement. Test case: verify password di database adalah hashed, tidak plaintext. Step 3: Server return token. Token này sẽ digunakan untuk all future requests. Ini adalah proof of authentication. Response should contain token, user info, expiration time. Test: verify token di response, verify user data correct, verify expiresIn value reasonable (not 0, not 999 years). Step 4: Client store token. Secure storage important. Not localStorage jika app sensitive data. Test: verify token dapat disimpan, dapat diakses, tidak corrupted. Step 5: Client use token. Format correct? 'Authorization: Bearer token'. Bukan 'Authorization: token'. Format must be exact. Test: wrong format, missing Bearer keyword, malformed token. Step 6: Server validate token. Signature validation - verify token tidak di-tamper. Expiration check - very important! Banyak bug di sini. Timestamp checking harus correct. Test: expired token, tampered token, token dengan invalid signature. Step 7: Return response. User data match what we expect? Tidak ada data leak? Test: verify correct user returned, verify no sensitive data exposed. Token expiration sangat important. Access token biasanya short-lived (1 hour). Refresh token longer-lived (7 days). When access token expired, client use refresh token untuk get new access token. Test: expired token behavior, refresh token logic, what if refresh token juga expired?"

🔐 LOẠI 1: Basic Authentication

Khái Niệm

Basic Auth: encode email:password menjadi Base64, send di header. Simple tapi NOT secure!

CLIENT PREPARATION: email:password = "john@example.com:MyPassword123" BASE64 ENCODING: Base64(john@example.com:MyPassword123) = am9obkBleGFtcGxlLmNvbTpNeVBhc3N3b3JkMTIz HTTP REQUEST: GET /api/users Authorization: Basic am9obkBleGFtcGxlLmNvbTpNeVBhc3N3b3JkMTIz SERVER VALIDATION: 1. Extract header value 2. Decode Base64 3. Split by colon: email = john@example.com, password = MyPassword123 4. Verify email exists 5. Hash incoming password, compare with DB 6. Return 200 OK or 401 RESPONSE: HTTP 200 OK { data: [...] }

❌ Kelemahan Basic Auth

  • Base64 is ENCODING, not ENCRYPTION! Sangat mudah decode. Tidak secure.
  • Password dikirim SETIAP REQUEST. Jika tanpa HTTPS → dapat di-sniff.
  • Password di-expose di HTTP header. Browser history, proxy logs, semua bisa lihat.
  • Tidak ada token expiration. Credentials valid selamanya sampai password di-change.
  • No permission granularity. Hanya semua-atau-nothing access.
  • Cache issue: Credentials mungkin di-cache browser, tidak aman.

TC_BASIC_004: Missing Authorization header Request: GET /api/users (no Authorization header) Expected: 401 Unauthorized { "error": "Missing authentication credentials" } Purpose: Request tanpa auth harus reject
TC_BASIC_005: Malformed Basic auth (invalid Base64) Request: GET /api/users Authorization: Basic !!!invalid-base64!!! Expected: 400 Bad Request atau 401 Unauthorized { "error": "Invalid auth format" } Purpose: Verify server validate Base64 format

✅ Kapan Gunakan Basic Auth?

  • ✓ Testing/Development environments saja
  • ✓ Internal APIs (tidak public)
  • ✓ Automated scripts yang tidak bisa handle tokens
  • ✓ HARUS pakai HTTPS (non-negotiable)

❌ Kapan JANGAN Gunakan?

  • ✗ Production APIs
  • ✗ Mobile apps
  • ✗ Public APIs
  • ✗ Tanpa HTTPS
  • ✗ Sensitive data
🔊 "Basic Authentication - paling simple tapi also paling dangerous. Cuma encode email:password jadi Base64, send di header. Selesai. Tapi kenapa dangerous? Tiga reasons: 1️⃣ Base64 BUKAN encryption. Siapa saja bisa decode. Minta ke user email + password setiap request. Jika tanpa HTTPS, attacker bisa intercept di network. PASSWORD LEAK! 2️⃣ Password dikirim setiap request. Contrast with tokens - tokens generated server, tidak perlu send password ulang. Dengan basic auth, password di-expose setiap request. 3️⃣ Tidak ada expiration. Jika device dicuri dengan password tersimpan, attacker bisa access forever sampai password di-change. Test cases? - Valid credentials → 200 OK - Invalid password → 401 - User tidak exist → 401 (jangan reveal apakah user exist atau tidak) - Missing auth header → 401 - Malformed Base64 → 400/401 - Wrong auth type (Bearer instead of Basic) → 401 - Empty email atau password → 401 Kapan pakai? Hanya development, internal APIs, automated scripts. HARUS pakai HTTPS. Production? TIDAK BOLEH."

🎫 LOẠI 2: Bearer Token Authentication (JWT)

Konsep Utama

MOST COMMON authentication method di modern APIs. Token generated server, client send di Authorization header.

Login Process dengan Bearer Token

CLIENT LOGIN: POST /api/auth/login { "email": "john@example.com", "password": "MyPassword123" } SERVER VALIDATES & CREATES JWT: 1. Validate credentials (check DB) 2. Generate JWT token dengan claims 3. Return token to client RESPONSE: HTTP 200 OK { "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9. eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9l...", "expiresIn": 3600, "user": {id: 1, name: "John", email: "john@example.com"} } CLIENT STORES TOKEN: Save token in localStorage/sessionStorage/secure storage CLIENT MAKES REQUESTS WITH TOKEN: GET /api/users/me Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9... SERVER VALIDATES TOKEN: 1. Extract token from header 2. Verify signature (using secret key) 3. Check expiration (exp claim) 4. Extract user info (sub claim) 5. Proceed with request RESPONSE: HTTP 200 OK {id: 1, name: "John", email: "john@example.com", ...}

JWT Structure (3 Parts)

JWT format: Header.Payload.Signature

PART 1: HEADER (Algorithm & Type) Base64 Encoded: { "alg": "HS256", // Signing algorithm "typ": "JWT" // Token type } Encoded: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 PART 2: PAYLOAD (Claims - User Data) Base64 Encoded: { "sub": "1234567890", // Subject (user ID) - critical "name": "John Doe", // User name "email": "john@example.com", // User email "role": "user", // User role - important for auth "iat": 1516239022, // Issued at (timestamp) "exp": 1516242622 // Expiration (timestamp) - critical } Encoded: eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lI... PART 3: SIGNATURE (Verification) HMACSHA256( Base64Url(header) + "." + Base64Url(payload), "your_secret_key_here" // Server secret ) Result: SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c FINAL JWT: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9. eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lI... SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

⭐ Critical Claims dalam JWT

Claim Nama Panjang Purpose Test Focus
sub Subject User ID (who is this token for?) Verify user ID correct, verify user retrieved correctly
exp Expiration Time Unix timestamp ketika token expired Verify expired token rejected, verify reasonable TTL
iat Issued At Unix timestamp ketika token created Verify timestamp is recent, verify correct ordering
role User Role User role (admin, user, guest) Verify role based access control, verify role not tampered
aud Audience API yang menerima token (api.example.com) Verify token valid hanya untuk API yang dituju
💡 Pro Tip untuk Testing: Decode JWT token menggunakan jwt.io (online tool) untuk melihat payload claims. Verify:
  • ✓ User ID (sub) match login user
  • ✓ Expiration time reasonable (1 jam, bukan 1 detik atau 1 tahun)
  • ✓ Role claim present & correct
  • ✓ Tidak ada sensitive data (password, credit card)
  • ✓ Signature is valid (jwt.io akan show green checkmark)
🔊 "Bagus! Sekarang Bearer Token - yang paling modern dan secure dibanding Basic Auth. Login flow mirip Basic Auth - kirim email + password. Tapi perbedaannya: server jangan langsung ask password lagi untuk setiap request. Instead, server generate token (JWT). Token ini adalah bukti authentication. Client simpan token, dan pakai untuk semua future requests. JWT structure: tiga parts - Header.Payload.Signature. Header: metadata tentang token - algorithm (HS256, RS256), type (JWT). Simple. Payload: THE MOST IMPORTANT - ini adalah user data dan claims. Claims itu custom fields. Standard claims: - 'sub' (subject) = user ID - critical untuk identify user - 'exp' (expiration) = token expired kapan. Timestamp format. HARUS check ini saat validate. - 'iat' (issued at) = token dibuat kapan - 'role' = user role, important untuk authorization Signature: Ini verify token tidak di-tamper. Server sign token dengan secret key. Jika attacker ubah payload, signature akan invalid. So when validating, server verify signature using secret key. If signature invalid → reject. Very important: Base64 encoding tidak encryption! Attacker bisa decode payload online di jwt.io. So jangan put sensitive data di JWT - no password, no credit card, no SSN. User bisa decode dan lihat. Advantage dibanding Basic Auth? 1️⃣ Password tidak dikirim setiap request - more secure 2️⃣ Token dapat di-expire - jika token leaked, akses hanya temporary 3️⃣ Token payload contain user info - no need query DB setiap request 4️⃣ Stateless - server tidak perlu store session Test untuk JWT: - Valid token → 200 - Expired token → 401 - Tampered token (modified payload) → 401 - Invalid signature → 401 - Token dengan wrong secret key → 401 "

Advanced JWT Testing

🔍 Security Testing - Common Vulnerabilities:
  • None algorithm: Attacker modify alg from HS256 to "none", server tidak verify signature. Test this!
  • JWT algorithm confusion: Mix asymmetric (RS256) with symmetric (HS256) keys
  • Claims missing validation: Server tidak validate all claims
  • Timing attack: Signature comparison menggunakan string comparison instead of constant-time
  • Key leakage: Secret key exposed (check GitHub, logs, etc)

🛡️ AUTHORIZATION TESTING - The Forgotten Part

Masalah Umum

70% bugs pada authorization, bukan authentication! Developers sering lupa implement authorization check.

Authorization Framework (3 Step)

FOR EVERY PROTECTED ENDPOINT: STEP 1: Is user authenticated? - Check Authorization header - Validate token - Extract user info Result: 401 if failed STEP 2: Does user have required role? - Check user.role against endpoint requirement - Example: endpoint require role="admin", user.role="user" Result: 403 if failed STEP 3: Does user have required permission? - Check granular permissions - Example: user can only modify own profile, not others - Example: user can only view documents assigned to them Result: 403 if failed EXAMPLE: PUT /api/users/{id} Requirement: - Authentication: REQUIRED (401 if missing) - Role: admin OR (user AND own_user) - Permission: Can modify own user OR admin can modify any user - Data validation: New data must be valid TEST MATRIX: ┌──────────────────────────────────────┬──────────────┐ │ Scenario │ Expected │ ├──────────────────────────────────────┼──────────────┤ │ No auth header │ 401 │ │ Invalid token │ 401 │ │ User role, modify own profile │ 200 OK │ │ User role, modify other user profile │ 403 Forbidden│ │ Admin role, modify any user │ 200 OK │ │ Guest role, any modify │ 403 Forbidden│ └──────────────────────────────────────┴──────────────┘

Role-Based Access Control (RBAC)

Role Permissions Test Focus
Admin All endpoints, all data, delete users, view logs Verify admin can access all protected endpoints. Verify admin can modify other users data.
User Own profile, own orders, not admin endpoints Verify user can access own data. Verify user CANNOT access other users data (403). Verify user CANNOT access admin endpoints (403).
Guest/Public Limited endpoints, read-only, no data modification Verify guest cannot create/modify/delete. Verify guest cannot access protected data.

Cross-User Access Prevention (Critical!)

🚨 MAJOR VULNERABILITY PATTERN: User A dapat access User B data
User A token (sub: 1, role: "user") GET /api/users/2/profile ← trying to access User B's profile Server check: ❌ BAD: Just check authenticated (token valid) ✓ GOOD: Check authenticated AND user.id == requested_user_id Expected: 403 Forbidden { "error": "Cannot access other user's profile" }

💾 Database Verification - The Secret Weapon

API Response ≠ Actual Data Saved

CRITICAL MINDSET: API return 201 Created doesn't mean data actually saved in database!

REAL BUG EXAMPLE: API REQUEST: POST /api/users { "name": "Jane", "email": "jane@example.com" } API RESPONSE: HTTP 201 Created { "id": 100, "name": "Jane", "email": "jane@example.com", "createdAt": "2024-01-01T10:00:00Z" } TESTER CHECK (incorrect): ✓ Status code 201? YES ✓ Response contain id, name, email? YES Conclusion: Test PASSED ✓ DATABASE CHECK (what should do): SELECT * FROM users WHERE id = 100 RESULT: EMPTY! (no rows) BUG FOUND: Data NOT saved to database! Possible causes: - Transaction not committed - Database connection lost - Write permission missing - Constraints violation (silent failure) - Side-effect failed (audit log, etc)

3-Step Database Verification

STEP 1: MAKE API REQUEST POST /api/users Request body: { name: "Jane", email: "jane@example.com" } Response: 201 Created { id: 100, name: "Jane", email: "jane@example.com", createdAt: "..." } Extract: id = 100 STEP 2: QUERY DATABASE SELECT * FROM users WHERE id = 100 Expected result: ├─ Row exist ├─ name = "Jane" ├─ email = "jane@example.com" ├─ created_at ≈ response.createdAt (within 1 second) ├─ updated_at = NULL or recent └─ Other fields match or default values STEP 3: VERIFY CONSISTENCY Response.name == DB.name ✓ Response.email == DB.email ✓ Response.createdAt ≈ DB.created_at ✓ (±1 second acceptable) Response.id == DB.id ✓

Database Test Cases

TC_DB_001: Verify CREATE data persistence API Request: POST /api/users { "name": "John", "email": "john@example.com" } API Response: 201 Created { "id": 1, "name": "John", "email": "john@example.com", "createdAt": "2024-01-01T10:00:00Z" } Extract: user_id = 1 DB Query: SELECT * FROM users WHERE id = 1 Expected: id: 1 name: "John" email: "john@example.com" created_at: "2024-01-01T10:00:00Z" (±1 second) Verify: ✓ Row exists ✓ All fields match response ✓ Timestamp within 1 second
TC_DB_002: Verify UPDATE data changes API Request: PUT /api/users/1 { "name": "Jane", "email": "jane@example.com" } API Response: 200 OK { "id": 1, "name": "Jane", "email": "jane@example.com", "updatedAt": "2024-01-01T11:00:00Z" } Extract: updated_time = 2024-01-01T11:00:00Z DB Query: SELECT * FROM users WHERE id = 1 Expected: name: "Jane" (changed from "John") email: "jane@example.com" (changed from "john@example.com") updated_at: "2024-01-01T11:00:00Z" (±1 second, updated) created_at: "2024-01-01T10:00:00Z" (unchanged) Verify: ✓ Fields updated correctly ✓ updated_at changed ✓ created_at NOT changed
TC_DB_003: Verify DELETE data removed Before DELETE: DB Query: SELECT COUNT(*) FROM users WHERE id = 1 Result: 1 row API Request: DELETE /api/users/1 API Response: 204 No Content After DELETE: DB Query: SELECT COUNT(*) FROM users WHERE id = 1 Result: 0 rows Verify: ✓ User completely removed ✓ No orphan record exists
TC_DB_004: Verify CASCADE DELETE Requirement: Delete user → All user's orders deleted Setup: DB: User 1 has 5 orders in orders table SELECT COUNT(*) FROM orders WHERE user_id = 1 Result: 5 API Request: DELETE /api/users/1 API Response: 204 No Content After DELETE: DB Query: SELECT COUNT(*) FROM users WHERE id = 1 Result: 0 rows ✓ DB Query: SELECT COUNT(*) FROM orders WHERE user_id = 1 Result: 0 rows ✓ (cascade deleted) Verify: ✓ User deleted ✓ All orders cascade deleted ✓ No orphan records
TC_DB_005: Verify Data Type Correctness API Request: POST /api/products { "name": "Laptop", "price": 999.99, "quantity": 10 } API Response: 201 Created { "id": 1, "name": "Laptop", "price": 999.99, "quantity": 10 } DB Query: SELECT * FROM products WHERE id = 1 Expected: name: "Laptop" (STRING type) price: 999.99 (DECIMAL/FLOAT, not STRING "999.99") quantity: 10 (INTEGER, not "10") Verify: ✓ Correct data types in database ✓ Not stored as string ✓ Can do arithmetic (price * quantity)
TC_DB_006: Verify Constraints Enforced Requirement: email unique constraint Setup: User 1 dengan email "john@example.com" API Request: POST /api/users { "name": "Jane", "email": "john@example.com" } Expected: 400 Bad Request atau 409 Conflict { "error": "Email already exists" } DB Query: SELECT COUNT(*) FROM users WHERE email = "john@example.com" Result: 1 (tidak 2, constraint enforced) Verify: ✓ Duplicate not inserted ✓ Constraint violation caught
TC_DB_007: Verify Default Values API Request: POST /api/users { "name": "John", "email": "john@example.com" } (no "status" field) API Response: 201 Created { "id": 1, "name": "John", "status": "active" } DB Query: SELECT status FROM users WHERE id = 1 Result: "active" (default value applied) Verify: ✓ Default value applied from database ✓ Not NULL, has correct default
TC_DB_008: Verify Transaction - All or Nothing Requirement: Transfer money (atomic operation) Scenario: Account A: $1000 Account B: $500 Transfer: A -> B $200 API Request: POST /api/transfers { "from_id": A, "to_id": B, "amount": 200 } If transaction commit: DB: Account A = $800, Account B = $700 ✓ If transaction fail (network error, etc): DB: Account A = $1000, Account B = $500 ✓ (Not: A = $800, B = $500 - inconsistent!) Verify: ✓ Both updates success OR both fail ✓ No partial updates
TC_DB_009: Verify Audit Log Created Requirement: Every user modification logged API Request: PUT /api/users/1 { "name": "Jane" } DB Query: SELECT * FROM audit_logs WHERE user_id = 1 ORDER BY created_at DESC LIMIT 1 Expected: action: "UPDATE" entity: "users" entity_id: 1 old_value: { "name": "John" } new_value: { "name": "Jane" } changed_by: current_user_id timestamp: recent Verify: ✓ Log entry created ✓ Correct action type ✓ Old and new values correct ✓ Timestamp recent
⚠️ Common Database Issues Found by Testing:
  • Data not saved at all (transaction not committed)
  • Data saved with wrong values
  • Relationships not created (foreign keys)
  • Constraints not enforced
  • Side effects not executed (audit logs, notifications)
  • Timestamp not created/updated
  • Default values not applied
  • Cascade deletes not working (orphan records)
  • Transactions not atomic (partial updates)

401 vs 403 - Never Confuse

✅ 401 Unauthorized:
  • Missing authentication
  • Invalid/expired token
  • Wrong credentials
  • Test: Request without token, wrong token, expired token
❌ 403 Forbidden:
  • User authenticated but not authorized
  • Role/permission mismatch
  • Cannot access other user's data
  • Test: User role accessing admin endpoint, cross-user access

4 Authentication Methods Learned

1️⃣ Basic Auth Format: Authorization: Basic Base64(email:password) Security: LOW (password sent every request) Use: Development only 2️⃣ Bearer Token (JWT) Format: Authorization: Bearer eyJhbGciOiJIUzI1NiI... Security: MEDIUM-HIGH (token-based, can expire) Use: Production APIs (most common) 3️⃣ API Key Format: Authorization: ApiKey abc123xyz or: X-API-Key: abc123xyz Security: MEDIUM (simple, no expiration) Use: Public APIs, internal services 4️⃣ OAuth 2.0 Format: Authorization: Bearer access_token Security: HIGH (delegated authentication) Use: Third-party integrations

🎓 Interview Preparation - Advanced Auth Testing

Common Interview Questions & Answers

Q1: "How do you test authentication?" Model Answer: "I test authentication at multiple levels: 1. Format validation: - Missing Authorization header → 401 - Invalid token format → 401 - Wrong auth type (Basic vs Bearer) → 401 2. Token validation: - Valid token → 200 - Expired token → 401 - Invalid signature (tampered token) → 401 3. Credential validation: - Valid credentials → 200 with token - Invalid password → 401 - Non-existent user → 401 (don't reveal user existence) 4. Token expiration lifecycle: - Token valid until exp timestamp - When expired, refresh token needed - Test refresh token logic - Test token revocation 5. Database verification: - After successful login, verify token stored correctly - Verify token claims match user data - Verify token issued_at timestamp reasonable"
Q2: "How would you test a role-based authorization system?" Model Answer: "I create a test matrix covering: 1. Role hierarchy: - Admin role → can access all endpoints - User role → can access user endpoints only - Guest role → limited read-only access 2. For each endpoint, test 4 scenarios: a) No authentication → 401 b) Authenticated but insufficient role → 403 c) Authenticated with correct role → 200/201 d) Cross-user access attempt → 403 3. Permission matrix: - Create operations → requires admin or owning user - Read operations → requires admin or owning user - Update operations → same restrictions - Delete operations → requires admin only 4. Privilege escalation: - User tries change own role to admin → rejected - User tries access admin endpoints → 403 - Ensure role comes from token, not request body 5. Database verification: - Verify user's role in DB matches token - Verify audit log shows who accessed what - Verify no data leaked to unauthorized users"
Q3: "You find that API returns 200 OK but data is not in database. What's your approach?" Model Answer: "This is common issue. My approach: 1. Identify the problem: - API response successful (201 Created) - But database query returns empty - Possible causes: transaction not committed, constraint violation, permission issue 2. Test cases to isolate: - Make API request → note returned ID - Immediately query database → is data there? - If not immediately → check 5 seconds later (timing issue?) - Check database logs for errors - Check application logs for errors 3. Root cause analysis: - Check if transaction committed (SELECT with uncommitted transaction) - Check for database constraints (unique, foreign key) - Check database permissions (write access) - Check database triggers (if trigger fail, insert might fail) - Check application connection pool (connection might close) 4. Verification: - Compare API response field by field with database - Verify data types correct - Verify relationships created (foreign keys) - Verify side effects executed (audit logs, notifications) - Test with different users (permission issue?) 5. Report: - Screenshot of API response - Screenshot of database query result - Steps to reproduce - Possible root cause"
Q4: "How do you test API security related to authentication?" Model Answer: "I test several security aspects: 1. Token security: - Token cannot be decoded without secret key → 401 - Token signature verification working - Token cannot be forged - Old tokens rejected after expiration 2. Credential security: - Password not stored plaintext in database - Password not returned in API response - Password not logged in audit trails - Password hashing using strong algorithm (bcrypt, not MD5) 3. Token transmission: - HTTPS required (not HTTP) - Token in Authorization header (not URL parameter) - Token not in logs - Token not cached in browser history 4. Authorization security: - User cannot access other users' data - User cannot escalate own role - User cannot bypass authorization checks - Rate limiting prevents brute force attacks 5. Common vulnerabilities: - JWT with algorithm='none' → should reject - Malformed token → should reject gracefully - Expired token still accepted → BUG - Missing authorization check → BUG - Password in request body → logged (security issue)"
